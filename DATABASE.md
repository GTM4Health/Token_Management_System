# Database Documentation: GTM4Health Token Management System

This document outlines the database architecture, schema definitions, table purposes, and data flow used in the **GTM4Health Token Management System (TMS)**.

---

## 1. Overview

The backend is built with **Flask** and uses **SQLite** as its relational database.
- **Database Engine:** SQLite 3
- **Database File:** `token.db` (located at the application root)
- **Initialization:** Automatically created and migrated on server boot via the `init_db()` function in `server.py`.
- **Integrity & Concurrency:** Operates with standard transactional safety (`BEGIN`, `COMMIT`) and thread-level SQLite connection handling.

The database consists of **two core tables**:
1. `tokens` — Manages queue numbers, lifecycle status, and serving counters.
2. `devices` — Manages registered hardware units (Calling Units and Token Dispensers) and tracks live online/offline heartbeat status.

---

## 2. Table: `tokens`

Tracks every token generated by physical dispensers or web kiosks, its current stage in the queue, and counter assignment.

### 2.1 Schema Definition (SQL)

```sql
CREATE TABLE IF NOT EXISTS tokens (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    token TEXT NOT NULL,
    status TEXT NOT NULL,
    counter TEXT DEFAULT 'Counter 1',
    generated_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 2.2 Column Descriptions

| Column Name | Data Type | Constraints | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | Auto | Unique sequential database row identifier. |
| `token` | `TEXT` | `NOT NULL` | *None* | 3-digit formatted token string (e.g., `'001'`, `'002'`, `'042'`). |
| `status` | `TEXT` | `NOT NULL` | *None* | Current lifecycle state: `'Waiting'`, `'Serving'`, or `'Completed'`. |
| `counter` | `TEXT` | *None* | `'Counter 1'` | Name or room of the counter handling the token (e.g. `'Room 1'`). |
| `generated_time` | `TIMESTAMP` | *None* | `CURRENT_TIMESTAMP` | UTC timestamp recorded when the token was dispensed. |

### 2.3 Token Lifecycle States

```
[ New Token Dispensed ]
          │
          ▼
    ┌───────────┐
    │  Waiting  │  Token is in queue; visible on display queue board.
    └─────┬─────┘
          │ POST /next
          ▼
    ┌───────────┐
    │  Serving  │  Currently active at a counter; displayed on main screen & announced.
    └─────┬─────┘
          │ Next token called / POST /reset
          ▼
    ┌───────────┐
    │ Completed │  Consultation finished; retained for historical records and repeat calls.
    └───────────┘
```

## 3. Table: `devices`

Stores hardware devices (ESP32 Calling Units and Token Dispensers) and powers the Admin dashboard's device configuration and live status indicators.

### 3.1 Schema Definition (SQL)

```sql
CREATE TABLE IF NOT EXISTS devices (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id TEXT UNIQUE NOT NULL,
    device_type TEXT NOT NULL DEFAULT 'calling_unit',
    unit_number INTEGER NOT NULL DEFAULT 1,
    unit_name TEXT NOT NULL,
    proceed_text TEXT NOT NULL,
    last_seen TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 3.2 Column Descriptions

| Column Name | Data Type | Constraints | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | Auto | Unique database entry ID. |
| `device_id` | `TEXT` | `UNIQUE NOT NULL` | *None* | Hardware identifier (e.g., MAC address `'68:09:47:2C:35:30'`). |
| `device_type` | `TEXT` | `NOT NULL` | `'calling_unit'` | Category of hardware: `'calling_unit'` or `'dispenser'`. |
| `unit_number` | `INTEGER` | `NOT NULL` | `1` | Sequential index per type (Unit #1, Unit #2, etc.). |
| `unit_name` | `TEXT` | `NOT NULL` | *None* | Friendly name (e.g., `'Calling Unit 1'`, `'Dispenser 1'`). Editable via Admin. |
| `proceed_text` | `TEXT` | `NOT NULL` | *None* | Destination announcement read aloud and displayed on TV (e.g., `'Room 1'`, `'Gate 2'`). Editable via Admin. |
| `last_seen` | `TIMESTAMP` | *None* | `CURRENT_TIMESTAMP` | Last heartbeat/activity timestamp. Used to determine **Online** vs **Offline**. |

### 3.3 Online / Offline Status Calculation

Devices send background heartbeat requests (`GET /api/device/ping?device_id=<MAC>`) every 20 seconds.
The server evaluates status dynamically:
$$\text{Status} = \begin{cases} \textbf{Online} & \text{if } (\text{now} - \text{last\_seen}) \le 60\text{ seconds} \\ \textbf{Offline} & \text{if } (\text{now} - \text{last\_seen}) > 60\text{ seconds} \end{cases}$$

## 4. Key Queries & Operations in `server.py`

| Operation | Target Table | Query Pattern |
| :--- | :--- | :--- |
| **Dispense Token** | `tokens` | `INSERT INTO tokens (token, status) VALUES (?, 'Waiting')` |
| **Fetch Next in Queue** | `tokens` | `SELECT id, token FROM tokens WHERE status='Waiting' ORDER BY id ASC LIMIT 1` |
| **Mark Serving** | `tokens` | `UPDATE tokens SET status='Serving', counter=? WHERE id=?` |
| **Complete Previous** | `tokens` | `UPDATE tokens SET status='Completed' WHERE status='Serving' AND counter=?` |
| **Device Heartbeat** | `devices` | `UPDATE devices SET last_seen=CURRENT_TIMESTAMP WHERE device_id=?` |
| **Device Listing** | `devices` | `SELECT id, device_id, device_type, unit_number, unit_name, proceed_text, last_seen, (strftime('%s', 'now') - strftime('%s', last_seen)) FROM devices` |
| **Queue Reset** | `tokens` | `DELETE FROM tokens` (clears active tokens while preserving device configuration) |

## 5. Persistence & Hardware Integration Note

- **ESP32 Non-Volatile Storage (NVS):** Physical token dispensers store `last_tok` in onboard flash memory (`Preferences`). When dispensing, the ESP32 passes its flash memory counter to the server (`/generate`), and the server computes $\max(\text{database\_max}, \text{hardware\_flash}) + 1$. This ensures token sequence numbers never revert to `001` unexpectedly, even if the server restarts.
- **Admin Configuration:** Renaming a calling unit's `proceed_text` (e.g., from `"Room 1"` to `"Doctor Office"`) updates the `devices` table immediately, and subsequent calls from that hardware unit announce the updated room name automatically.
